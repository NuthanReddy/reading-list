In Kafka, if there are multiple consumers reading from log at different offsets, doesn't it cause many random seeks? And doesn't this cause disk head to oscillate between read and write location often?

While it's true that having multiple consumers reading from different offsets can lead to random disk seeks, Kafka is designed to handle this efficiently. Here's how:
- Page Cache: Kafka relies heavily on the operating system's page cache, which keeps frequently accessed data in memory. This reduces the need for disk seeks as most reads can be served from memory.
- Sequential Reads and Writes: Kafka writes new messages to the end of the log and consumers read messages in the order they were written. This sequential access pattern is beneficial for hard drives where seeks are expensive.
- Zero-Copy: Kafka uses a technique called "zero-copy" to send data to consumers. This involves transferring data directly from the file system cache to the network buffer, reducing the CPU cost of copying data between kernel space and user space.
- Disk Head Oscillation: The concern about the disk head oscillating between read and write locations is valid for traditional hard drives (HDDs). However, many Kafka deployments use solid-state drives (SSDs), which don't have a physical disk head, so the cost of seeks is much lower.
- Log Segmentation: Kafka divides its log into segments. Each segment is a separate file. Older segments are not written to, they are only read from. This means that when consumers are reading from older data, the disk head does not need to move back and forth between the read and write locations.
In summary, while having multiple consumers can lead to more disk seeks, Kafka's design and reliance on modern hardware and operating system features mitigate these concerns. This allows Kafka to provide high throughput and low latency for real-time data feeds, even with many consumers.



How does kafka use page cache?


Apache Kafka takes advantage of the operating system's page cache to improve its performance in several ways:

Read Operations: When a consumer reads data, Kafka initially retrieves the data from disk. The operating system then caches this data in the page cache, a portion of RAM. Subsequent reads of the same data can be served directly from the page cache, which is much faster than disk access. This significantly improves read performance, especially when the same data is read multiple times.

Write Operations: Kafka writes are also benefited by the page cache. When a producer sends data, Kafka writes the data to the page cache first and returns an acknowledgment to the producer. The operating system asynchronously writes the data from the page cache to disk. This allows Kafka to handle write operations quickly without waiting for the disk I/O operation to complete.

Zero-Copy: Kafka utilizes a technique called "zero-copy" for sending data to a consumer. Instead of copying data from disk to an application's buffer and then to the kernel's buffer, zero-copy enables data to be transferred directly from the page cache to the network buffer, reducing CPU usage.

By leveraging the page cache, Kafka can provide high-throughput and low-latency data streaming, even with large amounts of data.



Isn't writes in page cache which are yet to be written to disk lost on node failure?

Yes, you're correct. If a Kafka broker node fails before data written to the page cache has been flushed to disk, that data can be lost. This is known as write-back cache, where the write operations are considered complete as soon as the data is updated in the cache.

However, Kafka has mechanisms to handle such situations to ensure data durability:

Kafka's producers can choose to wait for acknowledgments from the broker. This acknowledgment confirms that the data has been written to all in-sync replicas of the partition. This ensures that even if one broker fails, the data is safe as long as at least one in-sync replica is still running.

Kafka also allows you to configure the frequency of disk flushes according to your need for durability versus performance. The configuration parameter log.flush.interval.messages specifies the maximum number of messages to write to the log before forcing a disk flush. Similarly, log.flush.interval.ms specifies a time interval after which the log will be flushed to disk.

Using these mechanisms, Kafka can balance between performance and durability to mitigate data loss risks.

does kafka write every single message as it comes to disk as WAL? do kafka write to disk or page cache?

Yes, Kafka writes every single message to disk as it comes in. This is part of Kafka's Write-Ahead Log (WAL) strategy¹². Here's how it works:

1. **Immediate Write**: Instead of maintaining as much as possible and flushing it to the file system when memory space runs out, all data is immediately written to a persistent log on the file system².

2. **Page Cache**: This means the data is essentially transferred into the kernel’s page cache². The operating system decides when and how to write the data from the page cache to the disk¹.

3. **Asynchronous Disk Sync**: Kafka's writes to disk are asynchronous³. Other than at startup/shutdown, no Kafka operation waits for a disk sync to complete; disk syncs are always in the background³.

4. **Data Availability**: Messages are available to consumers only after they have been written to a particular segment of a partition⁴.

This design allows Kafka to provide high throughput and low latency for real-time data feeds, even with many consumers¹².

In Linux, the system uses a mechanism known as the page cache to handle disk I/O. When data is written to a file, it first goes to the page cache. Pages in the main memory that have been modified during writing data to disk are marked as "dirty" and have to be flushed to disk before they can be freed³.

The flushing of the page cache to disk in Linux is handled by the `pdflush` kernel threads¹. These threads are responsible for syncing dirty pages to the disk¹. When the system is being shut down properly, all the dirty buffers get synced/written to disk¹. However, this is not the same in case of abrupt power failures as data which is not yet flushed/synced to the disk is obviously lost¹.

The flushing of dirty pages to disk is triggered when either too much written data is pending (adjustable via `/proc/sys/vm/dirty_background_ratio`) or a timeout for pending writes is reached (`/proc/sys/vm/dirty_expire_centisecs`)⁴.

If you want to ensure that data is synced to the disk immediately after a write operation, you may want to consider calling `sync()` or `fsync()` system call in your application¹. If you don’t call `sync()` in your application, then dirty buffers get written to the disk upon certain kernel tunables¹.

Here are some of the kernel tunables that control how the application data gets synced¹:
- `vm.dirty_expire_centisecs`: how old (in 1/100th of a sec) the dirty pages must be before writing them to the disk.
- `vm.dirty_writeback_centisecs`: how often the kernel will wake up the `pdflush` thread to sync the dirty pages onto the disk³.
- `vm.dirty_background_ratio`: percentage of system memory which when dirty then system can start writing data to the disks.
- `vm.dirty_ratio`: percentage of system memory which when dirty the process doing writes should block to write out dirty pages to the disks¹.
